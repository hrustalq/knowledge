# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dynamic Knowledge Platform — a graph + semantic documentation store with REST API, GitLab-style revision DAG, and (eventually) an MCP interface for agents. `plan.md` is the authoritative architecture document; the approved Phase 0/1 implementation plan lives at `~/.claude/plans/indexed-sleeping-moler.md`; the product-feature layer (from `features.md`) is documented per-feature in `docs/features/`. Phases 0–5 are implemented (revision DAG + branches, compare endpoints, deterministic frontmatter relations, MCP server, merge requests with structural/semantic diff and If-Match concurrency, LLM relation extraction, hybrid search graph expansion, entity traversal + curation, and Phase 5 governance: auth/ACLs, audited operator graph queries, optional OpenSearch BM25, stale-doc detection + reindex scheduling, historical fact queries).

## Commands

The root `Makefile` is the entry point — run `make help` for the full list.

```bash
make setup              # first-time: env files → pnpm install → infra → migrations → build
make dev                # infra containers + api :3000 (Swagger /docs) + web :5173 + ingestion worker, watch mode (turbo)
make kill               # kill this repo's dev processes (api, web, worker, mcp, turbo); kill-all also stops infra
make dev-worker         # run only the BullMQ ingestion worker (already included in make dev)
make dev-mcp            # MCP server on stdio (knowledge_* tools) — for agent clients
make check              # lint + typecheck + build (CI gate)
make smoke              # health-check all six services

make infra-up|down|logs # docker compose: postgres, minio (+bucket init), redis, arcadedb
make db-migrate-new name=<x>   # create + apply a named Prisma migration
make db-migrate-deploy  # apply committed migrations only (prod-style)
make db-reset           # DESTRUCTIVE: drop DB, replay migrations
make env-check          # compare .env files against .env.example
make auth-bootstrap email=<e>  # Phase 5: create user + API key + workspace membership (AUTH_MODE=api-key)
make api-schema         # emit apps/api/openapi.json from the Nest app (no server/infra needed, env file required)
make api-client         # api-schema + openapi-typescript -> apps/web/src/api/schema.d.ts + web typecheck
make infra-up-opensearch       # infra incl. optional OpenSearch BM25 node (FULLTEXT_PROVIDER=opensearch)
```

Per-workspace: `pnpm --filter @knowledge/api run dev`, `pnpm --filter @knowledge/web run typecheck`, etc. There is no test suite yet — verification is the e2e flow (upload → finalize → poll `indexed` → search) plus `make check`.

## Architecture

Containment is three levels deep: **Workspace > Project > Document**. The workspace is the tenant/ACL boundary; the project is organizational only (docs/features/11).

Three-store separation (never mix responsibilities):

- **PostgreSQL** (Prisma, `apps/api/prisma/schema.prisma`) — transactional truth: documents, branches, immutable revisions + `revision_parents` DAG, `ingestion_jobs` (outbox), `revision_diffs` (table exists, endpoints are Phase 2).
- **MinIO** (versioned bucket `knowledge`) — raw bytes. Keys: `workspaces/{ws}/documents/{doc}/revisions/{rev}/source.md` + `normalized.json`. Clients upload directly via presigned PUT; the API never streams file bodies.
- **ArcadeDB** — graph + vectors (Document/DocumentRevision/Chunk vertices, HAS_REVISION/HAS_CHUNK edges). No official JS driver: `ArcadeClient` (apps/api/src/graph/arcade.client.ts) speaks plain HTTP (`POST /api/v1/command|query/knowledge`, Basic auth). **All graph queries must go through `GraphService`** — it is the single injection point for the mandatory workspace predicate (plan.md §6 security note). Phase 1 vector search is cosine-in-Node inside `GraphService.searchChunks`; swapping to native HNSW later should touch only that method.

Write path: `POST /v1/documents` → `POST :id/uploads` (presigned PUT) → `POST .../finalize` (SHA-256 hash, dedupe, revision → `finalized`, `ingestion_jobs` row committed in the same transaction = outbox) → BullMQ job → worker pipeline (fetch → gray-matter parse → heading-aware chunking in `src/ingestion/markdown.ts` → embed → upsert graph) → revision `indexed`. Status lifecycle: `draft → finalized → indexing → indexed | failed`. `OutboxSweeper` re-enqueues stale `queued` jobs; BullMQ `jobId` = `ingestion_jobs.id` makes double-enqueues harmless.

Key structural decisions:

- **The worker is a second entrypoint of `apps/api`**, not a separate app: `src/main.ts` (HTTP) vs `src/worker.main.ts` (`createApplicationContext(WorkerModule)`, no HTTP). `IngestionModule` (producer) is imported by both; `IngestionWorkerModule` (processor + sweeper) only by the worker — don't import it into `AppModule` or the API process will start consuming jobs.
- **`packages/contracts`** is a buildless TS package (`"exports": "./src/index.ts"`) holding plain request/response types shared by api and web. Keep it free of Prisma/server imports. Types are named to map 1:1 onto future MCP tools (`knowledge.search` → `SearchService`).
- **Embeddings** are pluggable behind the `EMBEDDING_PROVIDER` token: `stub` (deterministic hash vectors, default — full e2e with zero external deps) or `openai-compatible` (`EMBEDDINGS_BASE_URL` must include `/v1`; covers OpenAI/Ollama/LM Studio/vLLM). Configured via env, validated by zod in `src/config/env.ts` (fail-fast on boot).
- **Projects (docs/features/11)** — the containment layer between the tenant boundary and a page: **Workspace > Project > Document**. `projects` table (no FK on `workspace_id`, mirroring `documents.workspace_id`) + `documents.project_id` **NOT NULL** with a real FK; `documents.workspace_id` stays because the S3 key layout, the graph predicate, `ingestion_jobs`, `activity_log` and the fulltext index all key off it, so `project.workspaceId === document.workspaceId` is a service-enforced invariant (`ProjectsService.requireProjectInWorkspace`, called from `createDocument` and from project moves). Projects are **organizational only** — no members, no roles: the single auth change is a `'project'` `WorkspaceSource` resolving `:id` → owning workspace via `AccessService.workspaceOfProject`, so a project id from another tenant 403s. `ProjectsModule` is controller-bearing *and* MCP-imported (same shape as `IngestionAdminModule`) and exports `ProjectsService` for `DocumentsService`; keep it out of `WorkerModule`. Routes: `GET /v1/projects?workspaceId=` (viewer), `POST` (editor), `GET/PATCH /:id` (viewer/editor), `DELETE /:id` (admin, 409 `reason:'not-empty'` when it still holds documents, 400 on the workspace's last project — the two invariants ACLs cannot express). `POST /v1/documents` requires `projectId`; `PATCH /v1/documents/:id { projectId }` moves **the whole subtree** and re-roots the moved doc unless the same call supplies a `parentId` in the target project; `assertValidParent` now compares projects, not workspaces. `GET /v1/documents` + `/tree` take an optional `?projectId=` (absent = whole workspace, which is what the web falls back to before its projects store resolves). `filters.projectIds` on `POST /v1/search` filters post-ranking against PG under the existing 5× over-fetch, exactly like `filters.categories`. **The graph is deliberately untouched** — no `Project` vertex or edge, per feature 08's "the graph models semantic facts, not UI structure". MCP gained `knowledge_list_projects` + `projectIds` on `knowledge_search`. Web: `getProjectId()`/`setActiveProject()` + `kn_proj` cookie mirror the workspace mechanism (SSR reads it in `server.js` → `entry-server.ts`), `stores/projects.ts` resolves a stale stored id against the roster, project `<select>` under the workspace switcher, `/projects` page, project pickers in the editor and upload pages, breadcrumbs led by the project.
- **Phase 2 revision DAG & compare**: `document_revisions.branch_id` ties every revision to its branch; `finalizeRevision` advances *that* branch's head (falls back to the default branch for legacy rows). `POST /:id/branches` forks from a finalized revision (default: default-branch head); `GET /:id/revisions` returns the DAG (`parentRevisionIds` from `revision_parents`). `GET /:id/compare?from&to&mode=direct|merge-base` lives in `CompareService`: merge-base = BFS nearest-common-ancestor over the parent map, line diff via the `diff` package (`structuredPatch`), results cached in `revision_diffs` (immutable revisions → cache never invalidates; only finalized revisions are comparable).
- **Deterministic relations** (plan.md §5 fact classes): the worker's step 7 parses frontmatter `relations:`/`tags:` (`src/ingestion/relations.ts`) into typed edges with provenance (`extractor: 'frontmatter'`, confidence 1); reindexing deletes+recreates only that revision's frontmatter edges. Explicit relations come from `POST /v1/documents` `relations[]` or `POST /:id/relations` (`extractor: 'explicit'`, re-posting replaces by `(documentId, targetKey, type)`). Edge type names are SQL-interpolated, so everything is validated against `RELATION_EDGE_TYPES` in `GraphService` — never widen that list without keeping the allowlist check.
- **Phase 3 merge requests** (`MergeRequestsService`): `POST /:id/merge-requests`, `GET/approve/merge/close /v1/merge-requests/:id`. Merging is **fast-forward-preconditioned** — the target head must equal the merge base, otherwise 409 with a comparison link (3-way content merge is future work). `merge-commit` creates a two-parent DAG node (`revision_parents` order 1 = target head, 2 = source head), `squash` a single-parent one; both copy the source head's bytes and run the normal finalize → outbox → reindex pipeline. Compare gained `?structural=` (path-level diff of JSON/YAML bodies or markdown frontmatter, `src/documents/structural-diff.ts`, cached in `revision_diffs` as `structural-json`) and `?semantic=` (graph-projection diff: per-revision frontmatter relation edges + `GraphService.revisionEmbeddingShift`). Optimistic concurrency: `If-Match: <expected-head-revision-id>` on `POST /:id/revisions` → 409 + `comparisonUrl` when the branch head advanced (MCP equivalent: `baseRevisionId`).
- **Phase 4 inference & traversal**: LLM relation extraction is pluggable behind the `RELATION_EXTRACTOR` token (`src/extraction/`), mirroring embeddings: `none` (default — worker still runs the step to clear stale inferred edges) or `openai-compatible` (`EXTRACTOR_BASE_URL` with `/v1`, chat completions, JSON output). Inferred edges carry `extractor: 'inferred'`, clamped confidence (≥ `EXTRACTOR_MIN_CONFIDENCE`), `sourceChunkId` + `snippet`; extraction failures are non-fatal (revision stays `indexed`). Fact-class protection lives in `GraphService.replaceRevisionInferredFacts`: re-extraction deletes only that revision's inferred edges and skips any (type, target) already covered by a curated or explicit edge. Curation: `POST /:id/relations/curate` (confidence 1, replaces inferred/curated dups), `DELETE /:id/relations?type&targetKey&extractor`. Traversal (`src/entities/`): the graph is bipartite (edges always Document → Entity, `doc:<id>` node convention); BFS happens in Node over `GraphService.getWorkspaceRelationGraph` via pure helpers in `src/graph/graph-walk.ts` — one entity hop = two BFS hops. `GET /v1/entities`, `GET /v1/entities/trace` (declared before `:key` routes!), `GET /v1/entities/:key/neighbors`, `POST /v1/entities/:key/impact-analysis` (dependents = docs referencing the entity, then entities those docs DESCRIBE; dependencies = the reverse). Hybrid search: `expandGraph: { depth, relationTypes }` on `POST /v1/search` attaches `entities` to each hit and returns `related[]` docs reachable only through the graph, with connecting edges as evidence. MCP gained `knowledge_find_relations`, `knowledge_impact_analysis`, `knowledge_trace_relation`.
- **Phase 5 governance & scale**: auth is env-switched via `AUTH_MODE` — `none` (default) injects a synthetic dev principal with full access (web/demo flows keep working); `api-key` resolves `Authorization: Bearer kn_…` against `users.api_key_hash` (SHA-256; keys minted by `make auth-bootstrap email=…`, printed once). ACLs live in PostgreSQL (`workspaces`/`users`/`workspace_members`, roles viewer<editor<admin plus a `trusted_operator` flag): the global `AuthGuard` resolves the principal, then `AclGuard` enforces per-route `@Access(role, source)` metadata (`apps/api/src/auth/`) by resolving the target workspace in PG *before* the handler (and any graph query) runs — source is `body`/`query` (workspaceId field) or `document`/`merge-request`/`job` (`:id` param → owning workspace). `POST /v1/graph/query` + MCP `knowledge_query_graph` are the trusted-operator escape hatch: single SELECT only (keyword blocklist), row-capped (`GRAPH_QUERY_MAX_ROWS`), wrapped in an outer SELECT carrying the mandatory workspace predicate (rows without `workspaceId` are dropped — deny by default), audited into `audit_logs` (`GET /v1/audit-logs`, admin). BM25 mirrors the embeddings pattern behind `FULLTEXT_PROVIDER` (`none` default | `opensearch` — plain-HTTP client, no SDK; `make infra-up-opensearch`); the worker mirrors chunks into the index (non-fatal step 6b), hybrid search fuses vector+BM25 with reciprocal rank fusion, `mode: 'keyword'` is BM25-only (falls back to vector when no provider). Stale detection (`src/ingestion/stale.sweeper.ts`, worker, 5-min interval): re-queues jobs stuck `running`, retries `failed` under `STALE_MAX_ATTEMPTS` (fresh BullMQ jobId via `enqueueRetry` — the kept failed set blocks jobId reuse), and reindexes branch heads whose `document_revisions.embedding_model` signature (`provider:model:dim`, stamped at index time) drifted, 10 per sweep; manual surface: `GET /v1/ingestion/stale`, `POST /v1/ingestion/reindex`, `GET /v1/ingestion/jobs/:id`, MCP `knowledge_ingest`. Historical queries (`src/documents/history.service.ts`): each indexed revision keeps its revision-scoped fact set forever, so `GET /:id/facts?at=<rev>` snapshots via the newest asserting ancestor, `GET /:id/facts/timeline` derives introduced/removed revisions (removed-facts audit), and MCP `knowledge_get_historical_context` answers "what did the KB say about X at revision r".

- **Auth flow (login/signup/reset + users & access management)** on top of Phase 5: `users.password_hash` (scrypt via node:crypto, no deps), `sessions` (`ks_` tokens) and `password_reset_tokens` (`kr_`, single-use, TTL `AUTH_RESET_TTL_MIN`) — SHA-256 only in PG, mirroring API keys. In `AUTH_MODE=api-key`, AuthGuard resolves Bearer `ks_` against sessions and `kn_` against api_key_hash (disabled users → 401 on both). `POST /v1/auth/signup|login|forgot-password|reset-password` are `@Public()`; `logout|change-password` are authenticated; signup auto-joins `AUTH_DEFAULT_WORKSPACE_ID` (demo) as `AUTH_DEFAULT_ROLE`; reset links are logged (no mailer) and echoed as `debugToken` outside production. Reset/disable/password-override revoke sessions. RBAC: 401 = AuthGuard, 403 = AclGuard/AccessService; `users.is_admin` (platform admin) bypasses workspace ACLs, gates `@PlatformAdmin()` routes (`GET/POST/PATCH /v1/users` — self-disable/self-de-admin blocked), and `make auth-bootstrap` marks its user platform admin by default. Access management: `GET/POST /v1/workspaces` (creator → admin+operator), member CRUD under `/v1/workspaces/:id/members` with the `'workspace'` AclGuard source (`@Access('viewer'|'admin', 'workspace')`), last-admin protection in `WorkspacesService`. `UsersModule`/`WorkspacesModule` are API-only (same rationale as GraphQueryModule). Web: pinia `stores/auth.ts` resolves `/v1/me` once per app instance; router guard (`installAuthGuard`) → `/login` when 401 (api-key mode) or `/403` for non-platform-admins on `/admin/users`; `AUTH_MODE=none` keeps everything open (dev principal, no login UI). Token lives in localStorage + `kn_token`/`kn_ws` cookies; SSR reads them per-request via AsyncLocalStorage (`entry-server.ts` → `globalThis.__KN_SSR_CTX__`, no cross-request leaks) so authenticated pages server-render; the active workspace comes from `getWorkspaceId()` (falls back to the demo id). Pages: `/login`, `/signup`, `/forgot-password`, `/reset-password?token=`, `/403`, `/admin/users`, `/access`.

Response bodies type as `unknown` until controllers gain `@ApiOkResponse({ type })` — tighten per-route, or cast with contracts types at call sites.

- **AI settings (docs/features/12)** — the assistant layer made administrable per workspace instead of per boot. Five new tables (`ai_settings`, `ai_user_budgets`, `ai_skills`, `ai_plugins`, `ai_usage`); every settings column is an **override**, `null` = inherit the `ASSISTANT_*` env var, so an empty `ai_settings` reproduces feature 09 exactly. `AiConfigService.resolve(workspaceId)` folds DB → env → `PROVIDER_DEFAULTS` (moved out of `AssistantClient`) and reports per-field `sources` for the UI's "from env" badges; cached 30s per workspace, invalidated on write. **`AssistantClient` no longer reads config in its constructor** — every method takes an `AiCallContext` (`{ config, userId, operation, threadId? }`) and memoizes one `OpenAI` per `(baseUrl, apiKey, timeoutMs)`; `create`/`createStream` bill `AiUsageService.record` (fire-and-forget, like `ActivityService.record`) and streaming sets `stream_options: { include_usage: true }`, falling back to a flagged `estimated` token count for providers that ignore it. Credentials are AES-256-GCM (`ai/secret-box.ts`, `node:crypto`, keyed by `SETTINGS_ENCRYPTION_KEY`) — write-only over the API (`hasApiKey` + last-4 hint), an unset key disables secret *writes* only, and an undecryptable row falls back to the env credential. Budgets are checked (not reserved) before each call: `assertWithinBudget` → 429 `ASSISTANT_BUDGET_EXCEEDED` via the flat-extras pattern, opt-in per workspace (`enforceBudget`). **Skills** (`ai_skills`) are operator-authored instruction packs appended to `prepareTurn`'s system prompt — explicit `skillIds` from the composer first, then trigger-word matches, capped 3 skills / 8k chars; they are TRUSTED text (unlike document content) but the prompt states they can never widen access. **Plugins** (`ai_plugins`) are external MCP servers: `McpClientService` (SDK `Client` + `StreamableHTTPClientTransport`, SSE kept only for unmigrated servers) with a pooled idle-closed connection per plugin; tools are namespaced `mcp__<slug>__<tool>` (never shadows a built-in), offered from cached `discoveredTools` + the server's own input schema, routed in `AssistantService.runTool` before the built-in registry, and their output is wrapped as untrusted data. Plugin URLs are DNS-resolved and refused on private/loopback/link-local/CGNAT ranges unless `AI_PLUGINS_ALLOW_PRIVATE_URLS`. `ai_usage` is one row per upstream call and serves BOTH the usage aggregates and the call log (no prompt/completion text — that lives in `assistant_messages`). `AiModule` is API-only and `forwardRef`s `AssistantModule` both ways (a turn needs config/usage/skills/plugins; **Test connection** needs `AssistantClient`, which `AssistantModule` now exports). **Multiple providers**: `ai_providers` holds named profiles; `ai_settings.{chat,review,extraction}ProviderId` routes each purpose at one, and `assistant_threads.provider_id` lets a member pin their own. `AiConfigService.resolveFor(workspaceId, purpose, pinnedId?)` is first-hit-wins — pin → route → inline config → env — so a workspace with no profiles behaves exactly as before, and a disabled/deleted profile falls through instead of failing the turn. Deleting a profile clears every route and pin referencing it (the routing columns carry no FK, house style). Routing extraction forced a worker-safe split: `AiCoreModule` (AiProvidersService + AiConfigService + AiUsageService, no controllers) is imported by both `AiModule` and `WorkerModule`, and `ExtractorFactory.forWorkspace()` replaces the single env-wired `RELATION_EXTRACTOR` at the processor's call site. `ai_usage.provider_id` records which profile served each call. New `WorkspaceSource` values `ai-skill`/`ai-plugin`/`ai-provider`. Web: `/settings/ai` with five hand-rolled tabs (`AiSettingsPage.vue` + `components/ai/`), gated on workspace admin in the page; the usage chart is inline markup (no charting library is installed); the chat composer gained `SkillPicker.vue` sending `skillIds`.
- **Review mode (docs/features/13)** — a `Review` tab on the merge request that renders the page at the **source head** (`GET /v1/documents/:id/content?revision=`) through the normal read-side renderer and lets a reviewer annotate it PDF/Figma-style: select a passage → floating Comment button → thread; commented passages stay highlighted with a comment-count pin; clicking one opens a popover with its threads (reply/resolve inline). Anchoring is **quote-based**, not positional: `MergeRequestThreadAnchor` gains `{ type: 'text'; revisionId; quote; prefix?; suffix? }` (W3C TextQuoteSelector shape) — rendering has no line numbers, and a quote plus ~48 chars of context survives reflow and reordering. **No migration**: `merge_request_threads.anchor` is already Json with a String `anchorType`. `ThreadAnchorDto` accepts the new type (quote capped at 1 000 chars) and `validateAnchor` normalizes its whitespace exactly as the client's projection does. Web: `components/merge-requests/text-anchor.ts` builds a *projection* of the rendered DOM (visible text, whitespace collapsed, plus the `(text node, offset)` each char came from — block boundaries contribute a synthetic space so `</p><p>` cannot glue words), resolves ambiguity by scoring prefix/suffix, and wraps matches in one `<mark data-kn-thread>` per crossed text node, back to front, re-projecting per thread so overlapping comments nest; an unresolvable quote is reported **outdated** and never silently re-anchored. `MarkdownView` gained a `rendered` event (decorations attach after every other pass); `ReviewCanvas.vue` owns the canvas, selection affordance and popover (`data-kn-anno-ui` keeps its own text out of the projection); the detail page unions the diff's and the canvas's outdated sets for the timeline.
- **Glossary (docs/features/14)** — **project-scoped** vocabulary (`glossary_terms`: `workspace_id` + `project_id` FK, `term`, `aliases` Json, `definition`, `document_id` (no FK, mirrors `documents.parent_id`), `source` `manual|ai`, `enabled`), unique on `(project_id, term)` — the same word can mean different things in two projects. Two layers, the same split as frontmatter vs. inferred relations: **linking is deterministic and happens at read time** (`apps/web/src/lib/glossary.ts` — whole-word case-insensitive match, longest term first, boundaries spelled as `(?<![\p{L}\p{N}])` because `\b` breaks on `.env`/`C++`, skips code/headings/links/marks, max 3 links per term per page), so **no page is ever rewritten**; **the LLM is for authoring** (`POST /v1/glossary/suggest` → proposals only, never persisted; occurrences counted server-side against the source text and ungrounded proposals dropped; routed through `resolveFor(workspaceId, 'review')`; `AiUsageOperation` gains `'glossary'`). Routes: `GET /v1/glossary?workspaceId=&projectId=` (viewer; absent projectId = whole workspace), `POST`/`PATCH /:id`/`DELETE /:id` (editor), `POST /v1/glossary/suggest` (viewer, declared **before** `:id`). New `WorkspaceSource` `'glossary-term'`. `GlossaryModule` is API-only. Web: `stores/glossary.ts` (one lazy roster, `rescope()` called from the projects store beside the documents store's), a `glossary` prop on `MarkdownView` running the linker as its **last** pass (on for page content + review mode, off for comment/chat bodies), `/settings/glossary` built from `FilterBar` (project is a *pinned* scope field) + `Autocomplete` (page pickers) + `RichEditor` compact (definitions are markdown → rendered with `MarkdownView`, markers stripped for the link `title`), and a **Build glossary** quick action in `AskAssistant.vue` that renders proposals in the transcript with per-term Add.
- **Page comments + issue-shaped document page (docs/features/15)** — `DocumentDetailPage` was six tabs with the content as one of them; the main column is now **only the page**; every fact *about* it lives in a rail of **stacked collapsible widgets** (Overview/Frontmatter/History/Changes/Graph/Activity — `RailSection.vue`), each collapsed to one row carrying the fact that decides whether to open it (`#2`, `1 field`, `2 revisions`, `45 relations`, `4m ago`) from three light preview queries, each body mounted only while open (the graph builds a Cytoscape instance), each expandable into a dialog via **Maximize**. Overview is open by default; Frontmatter is filtered out entirely on pages that have none. `?tab=` survives as an *opening* instruction rather than two-way state (several widgets can be open at once), so every existing deep link still lands with the right widget open. Overview caps relations at 12 with a `+N more` toggle — a well-connected page carries fifty and walls off the content. **The content is `RichEditor` with `editable:false`**, not `MarkdownView` — read and edit are the same component — which forces the highlight mechanism to change: ProseMirror owns its DOM and reconciles away injected markup, so commented passages are **inline decorations** (`components/editor/extensions/comment-anchors.ts`, Tiptap's `addDecorations` with `update:'manual'` + a `setCommentAnchors` command, redrawn when the thread set changes rather than per keystroke) instead of feature 13's `<mark>` wrapping; the comment-count pin is a **widget** decoration, not `::after`, because PM renders one inline decoration as a span per text node and no selector can tell "this thread continues" from "a different thread starts adjacent". The quote-matching algorithm is now shared in `apps/web/src/lib/anchor-match.ts` (normalize → find all occurrences → score by surviving prefix/suffix → best wins); `text-anchor.ts` feeds it a DOM projection and `comment-anchors.ts` a ProseMirror projection, and the two agree character for character (whitespace collapsed, one synthetic space per block boundary) so an anchor written by either resolves in the other — unresolvable quotes are reported **outdated**, never silently re-anchored. Selection capture still reads the browser selection (a read-only editor keeps no PM selection) but takes the match and context from the doc projection, which doubles as the guard against quoting text the document does not have (a diagram's rendered labels, the comment UI). Backend: `document_threads` + `document_comments` mirror the MR pair — a second table pair on purpose, since a review thread dies with its MR while a page comment outlives every revision — with `DocumentThreadsService` and `GET/POST /v1/documents/:id/threads`, `POST /:id/threads/:threadId/comments`, `PATCH /:id/threads/:threadId`, all `@Access('viewer','document')` (whoever may read a page may annotate it; editing still needs `editor`) and **no open/closed gate**. Anchor validation moved to the shared `documents/review-anchor.ts`; contracts gained a `ReviewThread`/`ReviewComment` base that `MergeRequestThread` and `DocumentThread` extend, which is what lets one `ThreadCard`/`CommentComposer` (still under `components/merge-requests/`) serve both. **No discussion list under the content** — comments live on the text only, reached two ways: select a passage (floating Comment button) or hover a block (control in the reading gutter, the Notion/Figma affordance — a composer that opened on hover would fire continuously while reading; the control persists until another block claims it and is dismissed only by leaving the article, because travelling to it means crossing the gutter, where the target is padding and not a block — "no block here" must mean "nothing changed", or the pointer kills what it is reaching for); the popover threads are deliberately the same MR review UI, resolve included. The rail's "N open comments" calls `DocumentCanvas.flashThread()` (exposed) to scroll the passage into view and flash it. A block's quote is read from a clone with `.kn-anchor-pin, [data-kn-anno-ui]` stripped — the pin is a real text node, so plain `textContent` yielded a quote ending in a stray digit that matched nothing, making a block uncommentable once it had a comment. `.kn-read-surface` overrides the inherited authoring metrics — the 2rem/6rem cursor padding, the centred `--kn-measure` cap and `min-height:24rem` all go, so the page fills its column flush with its title; the hover control hangs in the page's *outer* margin (`.kn-comment-affordance`, `hover:hover` + `min-width:64rem` only) rather than in a reserved gutter, which would indent every page permanently for a button only visible under the pointer. `DocumentCanvas` also strips the body's leading `# Title` when it matches `documents.title` — the header renders the canonical title and nearly every page repeats it in its markdown, so the reader met it twice; a differing first heading is a real section and stays. New events `document.comment.created|resolved`; commenting is disabled while viewing `?revision=`; "On this page" is derived from the rendered editor with the static renderer's slugify so section links survive the swap.
- **Comment editing, Comment vs. Start thread, composer toolbar** on top of features 13/15: `merge_request_comments.updated_at` + `document_comments.updated_at` (nullable — "never edited" and "edited at once" stay distinguishable, and the UI's *edited* marker keys off it) behind `PATCH .../threads/:threadId/comments/:commentId` on both subjects, author-only (403 otherwise; MR edits also require the MR open). `{merge_request,document}_threads.resolvable` (default true, so every existing row is unchanged) is GitLab's two shapes of remark: `false` is a plain comment, `true` a thread that stays open until resolved — `setResolved` 400s on a plain comment, `statsFor` and the pages' `unresolvedCount` count only `resolvable && !resolved`, so a remark can never block a merge. `CommentComposer` gained `offerThread` (split Comment ▾ button, second item *Start thread*; `submit` now emits `(body, resolvable)`, which one-argument handlers keep ignoring), `initialBody` + `cancellable` (the same box rewrites a comment in place) and an exposed `expand()` that per-comment **Reply** calls; `ThreadCard` shows Reply/Edit on comment hover and hides Resolve on a plain comment. `RichEditor` in `compact` mode now shows `EditorToolbar` (also trimmed by a `compact` prop: no alignment/panels/status/columns/expand/toc) once the box is written in — "focused" scoped to the whole composer via `[data-kn-editor-shell]` plus teleported menus, so clicking Bold or the split button doesn't make the bar vanish mid-gesture. Both annotation canvases now dismiss the discussion popover on a `pointerdown` outside (document-level, not `onClickOutside` — a highlight *opens* the popover on click, so a `click`-based listener would close it in the same gesture; presses on another `[data-kn-thread]` switch passages instead).
- **Document import (docs/features/16)** — `/upload` was a textarea you pasted markdown into, on the one route whose job is getting an existing document *in*; it is now a three-step flow (**Destination · Parse · Review**) over a real file. New `import_jobs` table rather than an `ingestion_jobs` row, because `ingestion_jobs.revision_id` is NOT NULL and an import exists *before* any document does; the parsed markdown goes to `workspaces/{ws}/imports/{id}/parsed.md` beside the original, keeping the row the wizard polls small. Parsing is a **worker job the client polls** (a 300-page PDF outlasts any HTTP timeout, and the tab may close): `POST /v1/imports` (reserve + presigned PUT, type/size refused *before* the bytes move) → PUT → `POST /:id/start` (headObject confirms arrival, then enqueue) → `GET /:id` (status/`stage`/`progress`) → `GET /:id/content` → `POST /:id/submit` → `DELETE /:id`. Module split mirrors ingestion exactly: `ImportQueueModule` (producer, both), `ImportModule` (controller, API-only), `ImportWorkerModule` (processor + `ParsersModule`, worker-only). Parsers live behind one `DocumentParser` interface routed by `importFormatFor` in contracts — the same function the drop zone, the reserve guard and the registry call: `pdf` (unpdf; reconstructs headings from font-size rank, drops repeating running heads, breaks paragraphs on vertical gaps, flags `needsOcr`), `docx` (mammoth→turndown, style-mapped headings, images lifted to attachments, glyph bullets relisted, mammoth's warnings surfaced), `pptx` (fflate + slide XML, outline levels, per-slide images, notes as quotes), `html`, `tabular`, `structured`, `plaintext` (markdown passes through untouched), `ocr` (workspace vision model via `AiConfigService.resolveFor(ws,'review')`, billed as `AiUsageOperation` `'import'`, transcribe-never-summarise). Every parser returns what it could **not** carry and the review step shows it — a lossy import that says nothing is the failure the flow exists to prevent. **Submit is one server-side call**: creates the document *without* inline content, promotes the original + extracted images into `attachments`, rewrites staged `/v1/imports/:id/images/N` links to attachment URLs, then writes markdown once and finalizes — one revision whose image links always worked. New `'import'` `WorkspaceSource`; new `UNSUPPORTED_MEDIA_TYPE` API error code (415 previously fell through to `BAD_REQUEST`). Web: route is `meta.fill` (fixed header + stepper, flexing body, **one action bar** on every step), step 1 puts the clamped drop zone beside a destination rail, step 2 is one ring that *fills* on real upload bytes (XHR — `fetch` cannot report upload progress) then *sweeps* while the worker parses, step 3 is deliberately the same shell as `/documents/:id/edit` (title in `RichEditor`'s lede slot, prose column scrolling, rail for provenance/warnings). Step entrances are keyframe animations, not `-enter-from` classes: removing that class needs an animation frame, and a backgrounded tab never gets one, which strands the step invisible. `presignedPut` (`lib/presigned-put.ts`) is shared with the editor's attachment uploads.

Tools are named with underscores (`knowledge_search`, `knowledge_compare_revisions`, …) because MCP tool names forbid dots, but map 1:1 onto plan.md §9's dotted names. Any service injected into `McpService` must be *exported* by its module (SearchModule exports SearchService for exactly this).
- **Frontend SSR** (apps/web): create-vite-extra skeleton — `server.js` runs Vite middleware in dev / sirv in prod and splices `render(url)` output into `<!--app-head-->`/`<!--app-html-->`. Fresh app/router/pinia per request (`src/main.ts` factory); Pinia state is serialized to `window.__PINIA__` for hydration. ## Gotchas

- `apps/api` is **ESM** (`"type": "module"`, NodeNext): relative imports require the `.js` suffix (`./app.module.js`), including for `.ts` sources.
- class-validator `@IsUUID()` rejects nil-style UUIDs (version digit must be 1–5). The demo workspace is `11111111-1111-4111-8111-111111111111` (`DEMO_WORKSPACE_ID` in `apps/web/src/lib/api.ts`); auth is a hardcoded stub until Phase 5.
- `openapi-typescript` promotes any property that declares a `default:` in its Swagger decorator to **required** in the generated client, forcing every call site to pass a value the server already fills. Describe the default in `description:` instead (as `CreateGlossaryTermDto.source`/`enabled` do).
- A nullable DTO field needs an explicit `type:` in its Swagger decorator — `@ApiPropertyOptional({ nullable: true })` alone emits a typeless schema that `openapi-typescript` turns into `Record<string, never>`, so `make api-client` silently breaks the web typecheck at every call site passing a real value. Write `@ApiPropertyOptional({ type: String, nullable: true })` (as `UpdateMergeRequestDto.assigneeId` does).
- Content dedupe is **per-branch** (`@@unique([documentId, branchId, contentHash])`) — a merge revision legitimately repeats the source head's content on the target branch, so dedupe must not span branches (and never spans documents). `content_hash`/`s3_version_id` are nullable until finalize.
- `pnpm dlx` can hang on interactive prompts in non-TTY runs — `shadcn-vue` is a devDep; use `pnpm exec shadcn-vue add <component>` from `apps/web`.
- `corepack` doesn't exist on this Node install; pnpm is pinned only via the `packageManager` field.
- Controllers with auth dependencies must live in API-only modules: `GraphQueryModule` and `IngestionAdminModule` exist so worker/MCP contexts (which import `GraphModule`/`IngestionModule`) never instantiate controllers needing `AuditService`/`AccessService` — same reason `IngestionWorkerModule` stays out of `AppModule`. `AuthModule` is `@Global()` and registers both APP_GUARDs (provider order = execution order: AuthGuard → AclGuard).
- New routes need `@Access(role, source)` or they are authenticated-only with no workspace check in `AUTH_MODE=api-key`. With the default `AUTH_MODE=none` every request passes as the dev principal — test ACLs with a bootstrapped key, not in dev mode.
- A migration that adds a **NOT NULL column to a populated table** needs a data backfill, which `make db-migrate-new` cannot express (it runs `migrate dev`, applying immediately). Use `pnpm --filter @knowledge/api exec prisma migrate dev --create-only --name <x>`, hand-edit the SQL to add nullable → `UPDATE` → `SET NOT NULL`, then `make db-migrate`. `20260907160044_projects_layer` is the worked example.
- Reindexing is idempotent by design: `GraphService.upsertRevisionChunks` deletes the revision's chunks/vertex before recreating them, and the processor skips jobs already `completed`.
