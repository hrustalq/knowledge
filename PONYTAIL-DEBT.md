### `apps/api/src/workflows/workflow-materialize.sweeper.ts` — claims the row, not the work

### `apps/api/src/import/import.service.ts` — submit is check-then-act, unguarded

## Open findings — the root cause

**`DocumentsService.createDocument`/`finalizeRevision` commits its own transaction, and the caller's bookkeeping row is written afterwards, unprotected.** Six flows share the shape; each can produce a duplicate page or a dead-end row.

| flow                                              | bookkeeping written after commit | gap produces                              |
| ------------------------------------------------- | -------------------------------- | ----------------------------------------- |
| `merge-requests.service.ts:492→495`               | `merge_requests.status`          | MR permanently open **and** unmergeable   |
| `ai/agent-findings.service.ts:120→132`            | `findings[i].mergeRequestId`     | 409 `in-flight` forever, MR orphaned      |
| `import/import.service.ts:247→249`                | `import_jobs.documentId`         | wizard re-offers Submit → duplicate page  |
| `connectors/connector-staging.service.ts:269→271` | `connector_links`                | _(fixed 2026-09-14)_                      |
| `workflows/workflows.service.ts:470→471`          | `workflow_run_nodes.documentId`  | sweeper re-runs → duplicate page          |
| `workflows/workflow-trigger.service.ts`           | `workflow_run_nodes`             | _(fixed 2026-09-14)_                      |

None was fixable at the call site: `DocumentsService` takes no client argument. The boundary has to reach through `DocumentsService`, `StorageService` and (for agent findings) `MergeRequestsService`.

**The layer now exists** — `apps/api/src/prisma/transaction.ts` + `PrismaService.withTransaction` / `.onCommit`. An `AsyncLocalStorage` scope holds the transaction client and a proxy on the injected `PrismaService` prefers it, so the boundary reaches every service on the path with **zero call-site changes** across the 51 that inject Prisma. `i18n/t.ts` (`withLocale`) is the in-repo precedent and makes the same argument: ambient context "without widening a single service signature".

Two properties that are not optional and must survive any refactor:

1. **Nested `withTransaction` joins, it does not nest.** `createDocument` and `finalizeRevision` open transactions of their own; an outer boundary that did not absorb them would deadlock against its own connection.
2. **Post-commit work must go through `.onCommit`.** `finalizeRevision` enqueues its BullMQ job *after* its transaction — deliberately, per the comment at its outbox write. Joining inverts that: the enqueue would fire for an `ingestion_jobs` row that has not committed, or never will. Every queue enqueue, event publish and activity record inside a wrapped path belongs in `onCommit`, which fires on the OUTERMOST commit and not at all on rollback.

**Still to convert:** the three unfixed rows above. `agent-findings` additionally needs `release()` to clear `mergeRequestId`, not just `proposedAt`.

## Open findings — events

- **Vocabulary drift, both directions.** `KnowledgeEvent.type` is `string` and `publish()` is unchecked. Four types are declared and produced by nothing (`connector.item.staged|applied|failed`, `connector.link.created` — while `connector.link.removed` _is_ published). 26+ are produced and never declared (all 16 `ai.*`, four `assistant.*`, `workflow.created|updated|deleted`, `glossary.term.*`, `attachment.*`) and so can **never match a notification category filter**, since `typesForCategory()` inverts over `KNOWN_EVENT_TYPES`.
  **This is the defect the codebase names in its own docs** (`packages/contracts/src/ai/index.ts:738`: _"a closed vocabulary that promises one nothing produces is the defect this feature was written against"_). Third recurrence after `AGENT_RUN_TRIGGERS: 'event'` and `WorkflowStep.tools`.
  **Upgrade:** an `EventRegistry` in the `ConnectorRegistry` / `ParserRegistry` shape, keyed on the closed union, making both drift directions compile errors.
- **No event is transactional with the write that caused it.** 22 `$transaction` sites, none containing a publish or an `activity.record`. Best-effort is fine for cache invalidation; it is not fine for the two consumers that take durable action — `NotificationsService.fanOut` (lost event = missing inbox row) and `WorkflowTriggerService` (lost event = a run that never starts).
- `revision.failed` republishes on every BullMQ retry; no dedupe key on the bus.
- `EventsPublisher`'s Redis client uses ioredis defaults (`enableOfflineQueue: true`, no `maxRetriesPerRequest`), so a publish against a down Redis stalls the caller rather than failing fast. The "non-fatal" property is try/catch, not latency.
- No in-process bus: an event from `ActivityService` reaches the same process's own SSE clients via a full Redis round trip.

`apps/api/src/common/` is 326 lines across 5 files, all HTTP/URL cross-cutting. Nothing houses runtime patterns.

| add                                          | retires                        | why                                        |

## Fixed 2026-09-14

- `workflow-materialize.sweeper.ts` — the "guarded claim" wrote back the `status` it matched on, so the row never left its own predicate and **every** concurrent caller got `count === 1`. Now an optimistic lock on `updatedAt`. Residual crash-duplication marked above.
- `events.subscriber.ts` — the message listener was registered _after_ `await subscribe()` inside the same `try`. Redis not up at boot → subscribe rejects → listener never attached, and ioredis only auto-resubscribes channels that previously succeeded (`autoResubscribe` is gated on `condition.subscriber`), so the process stayed deaf for its lifetime behind one warn. Listener now registered first, with an explicit retry on `ready`.
- `workspaces.service.ts` — last-admin protection was `count()` then `delete`/`update`; two concurrent last-admin removals each counted one other admin and both proceeded, leaving a workspace with **zero admins** that no API route can repair. Now a single guarded statement with an `EXISTS` subquery. `create()` is now one transaction.
- `workflow-trigger.service.ts` — run + entry nodes now commit together, matching `WorkflowsService.startRun`. A run with no nodes enqueued nothing, never reconciled, and blocked every manual start for that page.
- `prisma/transaction.ts` (new) + `prisma.service.ts` / `prisma.module.ts` — the ambient transaction layer described above. Verified against the live database: 20 runtime assertions covering routing, read-your-own-writes, rollback, nested-join, `$executeRaw` binding, scope clearing, and `onCommit` ordering / rollback-suppression / throw-isolation; plus a boot of all three entrypoints (API, worker, MCP) confirming the proxy survives DI.
- `connectors/connector-staging.service.ts` — the page and its `connector_links` row now commit together (the first consumer of the layer). Previously a finalized page with no link row was invisible to `decideAction`, which re-imported the same external item on **every** subsequent pull, silently and without bound.
- `notifications.service.ts` / `events.publisher.ts` — `onCommentPosted` now returns its deliveries and `EventsPublisher.announce` publishes them. Mention, assigned and review-requested wrote an inbox row and **no live frame**, so the badge stayed stale until navigation. `NotificationsService` still takes `PrismaService` alone — the property that keeps `EventsModule → NotificationsCoreModule` acyclic.
