## Still open

### 3-way content merge

`documents/merge-requests.service.ts` — merging is fast-forward-preconditioned.
A diverged target 409s with a comparison link and the author rebases by hand.

- **ceiling:** every merge whose target moved is manual work.
- **upgrade:** real 3-way content merge. Large, and deliberately not attempted here.

The *concurrency* half of this entry is now fixed — the `SELECT … FOR UPDATE` on
the target branch row that the old `NOTE:` called "deliberately deferred" turned
out to cost nothing once the boundary spanned check + finalize.

### `EventRegistry` — the drift that keeps coming back

`KnowledgeEvent.type` is `string` and `publish()` is unchecked, so
`KNOWN_EVENT_TYPES` drifts in both directions and nothing catches it. The list
was corrected on 2026-09-14 (4 phantom types removed, 29 undeclared ones added)
but **correcting a list does not stop it drifting** — this was already the third
recurrence, after `AGENT_RUN_TRIGGERS: 'event'` and `WorkflowStep.tools`, and the
codebase names the defect in its own docs (`packages/contracts/src/ai/index.ts`:
_"a closed vocabulary that promises one nothing produces is the defect this
feature was written against"_).

- **ceiling:** a grep, run by hand, whenever someone remembers.
- **upgrade:** an `EventRegistry` in the `ConnectorRegistry` / `ParserRegistry`
  shape, keyed on the closed union, making both directions compile errors.
- **cost:** it ripples into every `ActivityService.record` caller, because an
  activity `action` becomes an event type. That is why it was not done in a
  debt pass.

### Durable event delivery

Ordering is now correct — every publish on a transactional path goes through
`onCommit`, so no event announces a row that has not committed, and none is lost
to a rollback. What is still true:

- A publish against a **down** Redis is dropped after a bounded wait. Fine for
  cache invalidation; not fine for the two consumers that take durable action,
  `NotificationsService.fanOut` (lost event = missing inbox row) and
  `WorkflowTriggerService` (lost event = a run that never starts).
- **upgrade:** an outbox for events, the way `ingestion_jobs` already is for
  indexing. The pattern is in the repo; only these two consumers need it.
- `revision.failed` republishes on every BullMQ retry; no dedupe key on the bus.
- No in-process bus: an event from `ActivityService` reaches the same process's
  own SSE clients via a full Redis round trip.

### Workers

- **No advisory lock or leader election anywhere.** Every API-side sweeper now
  has a re-entrancy guard, but that is per-process: two API replicas still sweep
  independently and rely on per-item claims being correct. Those claims were
  audited in this pass and are correct — but the guarantee is "every claim is
  right", not "one sweeper runs".
- Four of five queue modules import `IngestionModule` purely for its
  `BullModule.forRootAsync` side effect; the comments admit it. A
  `BullConnectionModule` would retire that.
- The five producers are one file five times (~200 LOC). Left alone on purpose
  (see *Rejected*) — but the **`attempts` difference between them is real and
  was undocumented**: ingestion uses `attempts: 3` with exponential backoff, the
  other four use `attempts: 1`.

## Fixed 2026-09-14

### The root cause — bookkeeping written after a committed document

`DocumentsService.createDocument`/`finalizeRevision` commit their own
transaction, and each caller's bookkeeping row followed unprotected. Six flows
shared the shape; **all six now commit together** via
`prisma.withTransaction()` + `.onCommit()` (`apps/api/src/prisma/transaction.ts`),
with zero call-site changes to the services in between.

| flow | gap produced | boundary now spans |
| --- | --- | --- |
| `merge-requests.service.ts` `merge()` | MR permanently open **and** unmergeable | branch lock → finalize → status flip |
| `import/import.service.ts` `submit()` | wizard re-offered Submit → duplicate page | claim → page → attachments → status |
| `workflows/workflows.service.ts` `sendNodeEvent()` | sweeper re-ran → duplicate page | `materializing` write → materialize → `documentId` → children |
| `workflows/workflow-materialize.sweeper.ts` | same, after a crash | materialize → `documentId` → children |
| `ai/agent-findings.service.ts` `propose()` | 409 `in-flight` forever, MR orphaned | branch → revision → finalize → MR → writeBack |
| `connectors/connector-staging.service.ts` | *(fixed earlier)* | — |

Three things that had to be got right and must survive any refactor:

1. **`createDocument` had two un-deferred side effects**, and they only became
   dangerous once callers wrapped it: `graph.addExplicitRelations` is **ArcadeDB
   over HTTP** (one DELETE + one create per fact, remote, unrollbackable) and
   `activity.record` publishes onto Redis. Both are now `onCommit`. Same for
   `createBranch`'s record and `MergeRequestsService.recordActivity`, which is
   the funnel for 8 call sites. `notifications.ensureSubscription` stays *inside*
   — it should roll back with the page.
2. **Prisma interactive transactions have no per-statement savepoint.** Once any
   statement fails at the database the whole transaction is aborted and
   everything after it returns `25P02`. Every `catch { continue }` around a
   Prisma call inside a boundary is therefore a landmine — `promoteOriginal` and
   `promoteImages` had one each, and both are now narrowed to the *storage* call
   they were actually there to tolerate.
3. **Failure writes and claims belong OUTSIDE the boundary.** `sendNodeEvent`'s
   `failed` write, the materialize sweeper's `failNode`, and
   `agent-findings.release()` all have to survive the rollback they are
   recording. Each is commented in place, because moving one inside silently
   restores the bug it fixes.

Two fixes that fell out of the boundary rather than needing their own work:

- **`import` submit's race needs no `updatedAt` column.** A guarded
  `updateMany({ where: { status: 'parsed' }, data: { status: 'submitted' } })` as
  the first statement is a real CAS: the predicate is on the column the write
  mutates, so under READ COMMITTED the racer blocks, re-evaluates, and gets
  `count === 0`. That is precisely the property the materialize sweeper's old
  claim lacked (it matched `status` and wrote `status` back, so every racer won).
  Rollback releases the claim, so no `submitting` status and nothing to strand.
- **The merge branch-row lock.** See *Still open* above.

`agent-findings.release()` also now clears `mergeRequestId`, not just
`proposedAt` — both re-entry guards read it, so a failure after `writeBack` left
the finding permanently unproposable.

### SSRF — checked at the dial instead of before it

`assertSafeExternalUrl` resolved the host to decide and handed the *hostname* to
whatever dialled it, which resolved again — so DNS rebinding slipped between the
two, and no amount of checking beforehand could close that: a check that finishes
before the socket opens is by construction a different resolution.

`common/safe-fetch.ts` moves the check **into the connection's own lookup**
(undici `Agent` with a `connect.lookup` that refuses private answers), so there
is no second resolution to disagree with it. Verified at runtime both ways —
`localhost` refused via `::1`, a public host reached.

Routed through it: `assistant/web-research.service.ts` (web_fetch), all 31
`connectorFetch` call sites plus the three raw `fetch` calls in
`markdown-git.adapter.ts` that bypassed it, and the MCP plugin transport (the
SDK accepts a custom `fetch`). `allowPrivate` flows via `ConnectorContext` so
self-hosted installs still reach their own network. Infrastructure fetches —
embeddings, ArcadeDB, OpenSearch, extractor, SearXNG — are deliberately
untouched: they dial configured internal hosts by design.

`assertSafeExternalUrl` stays as the admin-time check, because a settings form
needs to say "that host is internal" in words, immediately.

### Workers and shutdown

- `main.ts` never called **`enableShutdownHooks()`** — `worker.main.ts` and
  `mcp.main.ts` both did. The API skipped every `OnModuleDestroy` on SIGTERM.
- `agent-schedule.sweeper.ts` never stored its timer and had no
  `OnModuleDestroy` — the one sweeper that could not be stopped.
- Re-entrancy guards added to the five sweepers that lacked one (`outbox`,
  `stale`, `connector-schedule`, `connector-conflict`, `mention-reply`).
- `EventsPublisher`'s Redis client used ioredis defaults, so a publish against a
  down Redis stalled its caller through 20 reconnection attempts. Now
  `maxRetriesPerRequest: 1` + a 2s connect timeout. The offline queue stays **on**
  deliberately: with `lazyConnect` the first publish is what opens the
  connection, so disabling it would fail that one every time.
- `events.subscriber.ts` — found by booting the worker, not by reading: the
  `!subscribed` guard could not stop a double attach, because `subscribed` is set
  only *after* the await and `lazyConnect` means the first `subscribe()` is what
  triggers `ready`. Harmless at the protocol level, but every boot logged two
  "Subscribed" lines, which reads as two subscribers. Now guarded by an
  `attaching` flag cleared in `finally`.

### Events

`KNOWN_EVENT_TYPES` corrected: 4 declared-but-never-produced removed
(`connector.item.staged|applied|failed`, `connector.link.created` — note
`connector.link.removed` *is* published), 29 produced-but-never-declared added
(17 `ai.*`, 4 `assistant.*`, 3 `glossary.term.*`, 3 `workflow.*`, 2
`attachment.*`).

`notificationCategoryFor` needed **no change** — it is prefix-and-list based and
returns `null` by default, and none of the 29 match. They map to no category,
correctly: an admin editing a provider is trackable, not inbox news. The ledger's
earlier framing ("can never match a notification category filter") was the wrong
diagnosis; what was actually broken is that they were not **subscribable**, since
`LIVE_TRACKED_EVENTS`, the WS `subscribe` filter and the workflow trigger picker
all read this list.

### Earlier the same day

- `workflow-materialize.sweeper.ts` — the "guarded claim" wrote back the `status`

- `events.subscriber.ts` — the message listener was registered _after_

- `prisma/transaction.ts` (new) + `prisma.service.ts` / `prisma.module.ts` — the

- `connectors/connector-staging.service.ts` — the page and its `connector_links`
