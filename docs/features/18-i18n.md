# 18 — Internationalization

## What this is

The product speaks English and Russian. A person picks a language once; the
server-rendered HTML, every interface string, every API error, every validation
failure and every sentence the assistant writes come back in it. English is the
default and the fallback everywhere.

The choice lives in `users.locale`, is mirrored into a `kn_lang` cookie so the
SSR pass renders in it, and rides on `Accept-Language` so the API answers in it
too.

Document content is **not** translated. Pages, revisions, glossary definitions
and comments stay in whatever language their author wrote them; only the product
around them is bilingual.

## Why the cookie exists when the column already does

A language has to be known before any JavaScript runs, or the first paint is in
the wrong language and swaps after hydration — the one thing an i18n layer is
supposed to prevent. `users.locale` cannot be read that early: resolving it
needs a request, a token and a database round-trip.

So the column is the durable preference and the cookie is its mirror, exactly
the arrangement `kn_ws` and `kn_proj` already use for the active workspace and
project. `server.js` reads `kn_lang` before calling `render()`, the locale
enters the SSR context alongside the auth token, and `<html lang>` is stamped by
a fourth `.replace()` on the template — the `<!--app-head-->` placeholder sits
_inside_ `<head>`, downstream of the attribute, so it cannot do this.

Resolution order is the same on both sides: an explicit `?lang=`, then the
cookie, then `Accept-Language`, then English. The cookie beats the header
deliberately — the header is the browser's default, the cookie is a decision
someone made in this app.

## Why the API resolves its own locale

`users.locale` is deliberately _not_ an API-side resolver. nestjs-i18n resolves
in middleware, which runs before `AuthGuard`, so `req.principal` does not exist
yet. The web mirrors the stored preference into the cookie at sign-in and sends
`Accept-Language` on every call, which covers every request a person makes; an
API-key client falls through to the configured default.

Worker code has no request at all, so it carries its own: `import_jobs.locale`
and `workflow_runs.locale` freeze the initiator's language at creation, for the
same reason `workflow_runs.definition_snapshot` freezes the graph — the work
runs minutes or days later, and it writes prose.

## Why the library, and what it buys

`nestjs-i18n` on the API, `vue-i18n` on the web. Both were chosen over a
hand-rolled catalog after the hand-rolled version turned out worse at two things
that matter:

- **Plurals.** Russian needs four forms, and 11–14 are "many" despite ending in
  1–4. `{n} страница | {n} страницы | {n} страниц` selected by CLDR rules is
  correct; `n === 1 ? '' : 's'` cannot be. 27 such English-only pluralizations
  were removed from the web during this work.
- **Validation arguments.** `{constraints.0}` gives the real limit a decorator
  was configured with. The alternative was regex-scraping the number back out of
  class-validator's English default message.

`I18nContext.current()` (an AsyncLocalStorage) is the other reason: it makes the
language ambient at all 178 API throw sites without widening a single service
signature.

## Why fragments are translated whole

A sentence assembled from pieces is untranslatable. `"in " + projectName` works
in English and produces nonsense in Russian, which needs a case the English
fragment does not carry. So a fragment is either a whole translated phrase
passed in as a parameter —

```ts
t("documents.createFirst", { scope: t("documents.scopeProject", { name }) });
// Создайте первую страницу в проекте «Платформа».
```

— or a nested `t()` call at the point of use, which is how statuses, roles and
subject nouns reach a message already declined:

```ts
t("error.mergeRequest.notOpenForMerge", {
  id,
  status: t(`status.mr.${status}`),
});
// Запрос на слияние mr-9 закрыт — вливать можно только открытые запросы
```

Two API messages were restructured for this rather than translated: `AclGuard`'s
`uuid(value, what)` now takes a `subject.*` key instead of an English noun, and
`requireAnotherAdmin(…, verb)` takes a whole message key — an English infinitive
cannot be spliced into the middle of a Russian sentence.

## Why some prompts are deliberately English

Two LLM prompts do **not** get the locale directive, and both are commented in
place so they are not "fixed" later:

- **OCR** (`import/parsers/ocr.parser.ts`) transcribes an image, and its prompt
  already forbids translating. The output must match the image, not the reader.
- **Relation extraction** (`extraction/openai-compatible.provider.ts`) emits
  stable graph keys like `service:identity`. Localizing them would fragment the
  graph — the same entity from an English page and a Russian page would never
  link up.

Everything else gets it centrally: `AssistantClient.create`/`createStream`
append the directive to the outgoing system message, so a new entry point cannot
forget it, and its nine call sites needed no edits.

## Why module-scope labels hold keys

A label defined outside a component — `NODE_STATUS_LABEL`, `RUN_STATUS_LABEL`,
`TAB_LABELS`, `mrIcon().label`, the breadcrumb route maps — cannot call
`useI18n()`. Those maps now store **message keys**, resolved as `t(MAP[x])`
where a component can reach the translator.

`comment-anchors.ts` is the exception: a ProseMirror plugin has no render
context at all, so `RichEditor` injects a translator through the extension's
Tiptap options. Reaching for a global i18n instance would have been simpler and
wrong — the instance is created per app for SSR isolation.

## Data model

One additive migration, `20260909120000_i18n_locale`. Every column is
`TEXT NOT NULL DEFAULT 'en'`, so existing rows fill themselves and behave
exactly as before.

| Column                 | Why                                                              |
| ---------------------- | ---------------------------------------------------------------- |
| `users.locale`         | The durable preference; follows a person to another browser.     |
| `import_jobs.locale`   | Parser warnings and OCR run in a worker, long after the request. |
| `workflow_runs.locale` | A run writes whole pages, days after it was started.             |

The columns are `TEXT` rather than an enum so adding a language is a catalog
change, not a migration. `asLocale()` narrows a stored value and degrades an
unknown one to English rather than passing it to the library.

## Shape

**Contracts** (`packages/contracts`): `SUPPORTED_LOCALES`, `Locale`,
`DEFAULT_LOCALE`, `isLocale`, `parseAcceptLanguage`. `MeResponse` gains
`locale`; `UpdateMeRequest` is new.

**API** (`apps/api/src/i18n/`): `i18n.config.ts` holds `i18nAsyncOptions`,
imported by all three entrypoints. `t.ts` exports the ambient `t()` and
`withLocale()`, the AsyncLocalStorage scope the WebSocket gateway and the
BullMQ processors run inside. Catalogs are `{en,ru}/*.json`, copied into `dist`
by the `assets` entry in `nest-cli.json` and located with `import.meta.dirname`
(there is no `__dirname` — apps/api is ESM).

**Web** (`apps/web/src/i18n/`): `createI18nFor(locale)` is called inside
`createApp()`, never at module scope — two concurrent SSR renders would
otherwise share `locale`. Catalogs are `messages/{en,ru}.json`, and `ru.json` is
typed against `typeof en` so a missing key fails `vue-tsc`. `lib/format.ts`
holds the `Intl` wrappers: every previous `toLocaleString` call passed no locale
at all, meaning "follow the host" — the browser on the client and the _server's_
locale during SSR, which is a hydration mismatch waiting to happen.

**Routes**: `GET /v1/me` returns `locale`; `PATCH /v1/me` writes it, and no-ops
for the dev principal, which has no `users` row. `Accept-Language` is stamped on
all 143 OpenAPI operations by the existing post-processing loop in
`config/swagger.ts` rather than by decorating each handler.

**Env**: `I18N_DEFAULT_LOCALE` (default `en`). It must have a default —
`scripts/generate-openapi.main.ts` runs the zod validation with no infrastructure.

## Typography

Sora ships no Cyrillic (latin, latin-ext and vietnamese only), so Russian
headings fell back to system-ui and lost the display voice. `--font-display` is
now `"Sora", "Manrope", …`: browsers fall back per glyph, so Latin still renders
in Sora and the English design is untouched.

Russian runs 15–20% longer, and the settings rail is a fixed-width column whose
hints are one line by design. Those were shortened in Russian (`Кто имеет
доступ`, `Лента событий`, `Цепочки шагов`) rather than the rail widened, which
would have indented the column for every language to fit one.

## Why a known-set label still needs a fallback

`documents.category` is free text in the database. The eight
`DOCUMENT_CATEGORIES` are what the UI offers, not what the column accepts —
imported and API-created pages carry values like `onboarding` or
`Order Management`. Translating one blindly renders the key at the reader, so
`labelFor(t, 'category', value)` in `lib/labels.ts` falls back to the raw value
when no message exists. The same shape covers activity action codes and the
tool vocabulary: an unknown code reads as itself, never as `category.foo`.

## Gotchas

`I18nModule.forRootAsync` types its factory result as
`I18nOptionsWithoutResolvers`. `resolvers` and `loader` returned from
`useFactory` are **silently dropped**, and every request quietly falls back to
`fallbackLanguage`. They belong on the async options object itself.

Message keys are resolved by splitting on `.`, so a key that _contains_ a dot —
an activity action code like `merge-request.comment.created` — must be stored as
real nesting, not as a literal dotted key.

A `v-for` variable named `t` shadows the translator, and the failure is a
confusing `This expression is not callable` rather than a missing translation.
Two of these existed.

A prop default is evaluated at module scope, outside any app's i18n instance, so
a default like `FilterBar`'s `emptyLabel: 'Filter'` has to be resolved at render
(`emptyLabel ?? t('common.filter')`) instead.

A map converted to hold message keys is only half the change — the render site
has to resolve them. The breadcrumb route maps shipped a version that rendered
`nav.ai` at the user, which typechecks perfectly and looks fine in English
review because nobody reads the settings breadcrumb in the language it already
worked in.

## Limits

Document content is untranslated and there is no per-locale variant of a page —
that would touch the revision DAG, ingestion and the graph, and is its own
phase. Import parser warnings are stored already-translated rather than as
`{ key, params }`: a warning is read in the review step minutes after the parse
by the person who started it, so re-translating a stored one buys nothing. The
`Knowledge` wordmark and the `Dev (AUTH_MODE=none)` principal name are English
by design. Swagger operation descriptions, MCP tool descriptions and
JSON-schema tool parameters stay English — they are contract text for
developers and models, not user copy. Layouts were checked in the browser at 1024, 1100 and 1440 px on the main
surfaces; narrow/mobile widths and the workflow canvas were not, and are the
places to look first if something clips.
