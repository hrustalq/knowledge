# API performance baseline — 2026-11-18

Baseline for [#1242](https://github.com/hrustalq/knowledge/issues/1242), measured on `origin/dev` `f34f2124` plus this issue's measurement tooling. No performance fix is included.

## Method

- **Build:** `nest build` output run as `node dist/main.js` and `node dist/worker.main.js`, with `OPS_JSONL_ENABLED=true`, `OPS_QUERY_COUNT_ENABLED=true`, `LOG_PRETTY=false` and `AUTH_MODE=none`. The web was the production SSR build on port 5175.
- **Machine:** Apple M3 Pro, Node 26.4.0. PostgreSQL 17.12, ArcadeDB 26.11.1, OpenSearch 2.19.7 and Redis in local Docker. Embeddings came from bge-m3 on a local Ollama.
- **Corpus:** the local demo workspace, with 745 pages, 6,687 live chunks in ArcadeDB and 2,734 in the BM25 index. The #1241 fixture provides a 95-page project and a 163,782-byte page with 150 sections.
- **Traffic:** one session with two parts. First, the #1241 web walk (`apps/web/scripts/measure-performance.mjs`, three runs per route and profile), which drives the API the way SSR and the browser do for Pages, a long page, the editor, search, the assistant and a share link. Second, `apps/api/scripts/measure-api.mjs`, the e2e flow: 10 typical pages (about 4 KB, eight sections each) created, finalized and polled until `indexed`, then 20 rounds of the main reads and two hybrid searches each. In all, 6,938 API requests, 46 searches and 11 ingestions.
- **Query count:** Prisma operations per request, from the new counter (below). One operation can be more than one SQL statement (an `include`), and `queryMs` sums operations that ran concurrently, so it can exceed the wall time.

These are controlled local lab numbers. A single user ran the session with no concurrency, so they are not production latencies and not an agreed SLO. `AUTH_MODE=none` skips the session/API-key lookup, so production requests run one or two more queries each.

What the table says:

- **Search is the only slow route a reader waits on.** It spends 21 ms in PostgreSQL out of 591 ms. The rest is outside PG (next section).
- **`GET /v1/documents/graph`** spends 17 of 121 ms in PostgreSQL, so the rest is ArcadeDB and serialization. This is recorded, not filed: this corpus is small and the audit set no budget for the graph view.
- **`GET /v1/release-tags`** has one 282 ms outlier among eighteen calls at 4–32 ms, which was the first call after boot. No finding.
- **Query counts are flat.** No read route runs more than 8 operations. The exceptions are a page create (`POST /v1/documents`, 30 operations for create, finalize and the outbox row, in 36 ms) and `agents/choices` on a cache miss (41, filed as #1290).

## Search, by leg

46 searches (hybrid, k = 10, with and without `groupBy: 'page'`), from the `search.executed` events.

| Stage | p50 | p95 | max |
| --- | ---: | ---: | ---: |
| search total | **597.6** | **1,300.2** | 1,709.0 |
| vector leg (ArcadeDB + embedding) | **425.1** | 760.3 | 815.0 |
| query embedding (inside the vector leg) | 41.4 | 67.0 | 347.9 |
| BM25 leg (OpenSearch, parallel to vector) | 10.9 | 43.7 | 185.9 |
| PG join: permissions and trust (post-filter) | 15.9 | 36.8 | 58.0 |

4 of 46 searches returned nothing.

- The vector leg is ArcadeDB, not the embedder: 425 − 41 ≈ 384 ms per search. Timed directly, `vector.neighbors` with its `filter: (SELECT @rid FROM Chunk WHERE …)` subquery took 64–254 ms, against 6–20 ms for the same call with no filter. The filter subquery materializes every live chunk of the workspace on each search. Filed as **#1288**.
- The legs and the join account for about 440 ms of the 591 ms p50. About 150 ms per search is spent after the join and is not attributed by any timing. Filed as **#1291**.
- The PG post-filter is cheap (16 ms p50) and is not a target.

## Query count per request

`OPS_QUERY_COUNT_ENABLED=true` (default off) adds `queries` and `queryMs` to every `http.request` event. It is a Prisma client extension (`apps/api/src/prisma/prisma.service.ts`) that counts each operation against the request's trace scope. That covers model calls, raw SQL and operations inside `withTransaction`. It is not `$on('query')`, because the engine emits that event outside the caller's async context and so cannot tell which request ran a query (`test/query-count.e2e-spec.ts` pins this).

It wraps every operation, so it stays off in production. Turn it on for a profiling session, as here. Jobs, MCP calls and ArcadeDB/OpenSearch are not counted. A route that queries ArcadeDB shows its time in the gap between `durationMs` and `queryMs`.

## Reproduce

Start the built API and worker from `apps/api` with the flags, and the production web on 5175:

```bash
pnpm --filter @knowledge/api run build && pnpm --filter @knowledge/web run build
cd apps/api
export OPS_JSONL_ENABLED=true OPS_QUERY_COUNT_ENABLED=true LOG_DIR=/abs/path/perf-logs LOG_PRETTY=false
node dist/main.js & node dist/worker.main.js &
(cd ../web && NODE_ENV=production PORT=5175 API_URL_INTERNAL=http://localhost:3000 node server.js &)

# the web walk (see docs/performance/2026-11-18-web.md for its variables), then:
PERF_WORKSPACE_ID=<workspace> PERF_DOCUMENT_ID=<long-page> node scripts/measure-api.mjs

cd ../.. && LOG_DIR=/abs/path/perf-logs make backtest ARGS="--report"
```

`measure-api.mjs` takes `PERF_API_URL` (default `http://localhost:3000`), `PERF_RUNS` (default 20) and `PERF_PAGES` (default 10). It leaves a `perf-walk <timestamp>` project with its pages behind. Use a fresh `LOG_DIR` so the report reads this session only. Without it, `--report` reads `<repo>/logs`, which holds every earlier dev session. The report now honours `LOG_DIR`; before #1242 it always read the default.
